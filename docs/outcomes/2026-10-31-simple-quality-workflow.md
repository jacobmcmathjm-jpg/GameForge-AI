# Ordinary asset requests and quality-gated preparation — 31 October 2026

This app-only increment connects short everyday asset instructions to the supported offline pipeline. It is not universal game creation, a learned geometry/animation repair engine, or a guarantee that every result looks refined. Existing advanced Blender/mission/review prompts remain explicit lower-level workflows.

## Use

`Make me a detailed wooden crate.`

`Create a realistic barrel called yard-barrel.`

`Make a guard named test-guard.`

Supported labels/aliases: barrel, wooden crate/crate, concrete barrier, industrial fence/fence, shipping container/container, rigged mannequin/mannequin, industrial security character/security guard/guard. Optional qualifiers include refined, detailed, realistic, game-ready and high-detail. They select the current fixed supported quality profile, not a different neural model or a promise of photorealism. No Blender or experience-guided wording is needed for this short syntax.

Optional names are bounded; otherwise a stable `quality-<family>` name is used. Existing destinations are never overwritten. Repeating the same unnamed request can stop at an occupied target rather than create a fresh target; provide a new name for a separate technical candidate. Unknown objects, injected commands and unsupported short model requests do not fall through to inference/providers. Arbitrary longer level/game briefs remain separate existing workflows; this increment does not claim to fulfil them.

## Actual workflow

1. Read the local library and prefer compatible sources with both current source reviews. Check current recipe/dimensions and avoid rejected/invalid-review sources. Missing valid complete history permits one fixed local baseline generation.
2. Use the refined prop recipe IDs automatically. Character requests use the existing original bounded rigged-character recipes; no new guard geometry or motion is authored here.
3. Verify immutable source/preview and structured source-quality evidence: current profile/recipe/hash, topology budget, map resolution/normal-map presence, editable source, appropriate LOD companions or source skin structure. These are technical checks, **not an appearance score**. Old technical profiles are not silently upgraded to refined profiles.
4. Request the existing exact live visual and rights reviews, separately. Reuse exact current approved source decisions when available. A known rejection, cancellation, failed generation, malformed receipt or insufficient action budget stops as **unfinished**. No fake approval, blind retry or seed reroll is performed.
5. Import only with both exact source-review hashes bound. The executor holds the shared source-decision lease, revalidates both current approved records before staging and again immediately before publication, and refuses missing/revoked/changed/tampered decisions. No overwrite. The receipt retains the source review hashes; the unchanged provenance schema makes the source-only/target-pending scope explicit.
6. Existing bridge/kit/compile/prop preparation or rig/animation diagnostic steps run through their normal approvals. The terminal response calls the result a **technical candidate**, with target appearance/runtime/placement acceptance still pending. No finished/refined final-product or level claim is made.

The fresh prop planner fixture needs ten actions and the final response fits the existing twelve-pass budget. Only the current known recipes are generated. This is source selection, validation and review-gated preparation—not an autonomous perceptual optimisation loop. A rejected model still needs a real bounded recipe/parameter revision; arbitrary visual or animation repair is future work.
