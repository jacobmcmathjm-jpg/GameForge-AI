# ForgeCore Architecture

ForgeCore is a local-first Windows desktop application. The desktop is a thin MVVM composition layer; policy and orchestration live in testable class libraries.

## Dependency direction

`Desktop -> Agent -> LocalAI, Tools, Security, Memory -> Core`

- **Core**: domain records, task states, permissions, tool contracts, cancellation service.
- **Security**: canonical workspace boundary checks, symlink/reparse-point defence, command allow-list, approval policy.
- **Tools**: file, exact patch/snapshot, metadata-only project index/search, Openverse catalogue search, optional 3D-generation providers, deterministic project-scaffold, passive asset staging/inspection/import, immutable reviewed-asset vault search/store/import, dedicated .NET, versioned Unity bridge, and allow-listed process implementations. Tools receive already validated calls but independently repeat workspace, network, reparse-point, index-limit, template, host, type, structure, size, hash, timeout, and output checks (defence in depth).
- **Memory**: local SQLite persistence for conversations, messages, tasks, tool calls, audit events, project-index summaries, and metadata-only file records. Raw online catalogue result sets are deliberately redacted.
- **LocalAI**: deterministic mock plus an opt-in LLamaSharp 0.27/Vulkan backend. Weights load lazily, one inference runs at a time, generated `{Response, Actions}` JSON is grammar-constrained and strictly parsed, conversation history is bounded, and permissions are derived from tool kinds. A narrow deterministic router owns the credit-consuming 3D workflow so that action is not exposed to the native llama grammar; its calls pass through the same parser-equivalent domain validation and every ordinary security boundary.
- **Agent**: bounded, cancellable plan/validate/approve/execute/observe/replan loop with aggregate action limits and duplicate suppression.
- **Desktop**: professional three-pane WPF/MVVM shell, conversation bubbles, local/model/task/audit status, DI composition, structured logging, scoped permission dialog, native dark title bar, and emergency stop.

The desktop reads bounded recent-conversation, message, task, and audit projections from the store. Process CPU and working-set metrics come from a read-only `ISystemMetrics` service; GPU reporting remains unavailable rather than using a privileged or vendor-specific probe.

## Agent flow

Explicit game-creation requests first enter `GameProductionService`, which derives a `GameProductionPlan` and persists its blueprint before exposing the dependency queue for execution. The queue has its own reviewed 32-step bound, preserving all 1–12 requested levels and their verification steps independently of the general chat loop's action budget. It uses the existing typed tools and security checks; an active `IAutomaticApprovalGrant` may authorize a queued action only after policy validation. Asset-role searches are discovery stages, while the persisted art/system brief and reporting retain the remaining production obligations. Questions and requests for individual assets, maps, menus, or files continue through the ordinary model route. Unsupported genres/hybrids are reported without substituting a different game.

1. Persist the user message and task.
2. Ask `ILocalModel` for a typed plan, including bounded observations from earlier passes in the same task.
3. Enforce aggregate action, planning-pass, retry, observation, and rendered-result limits.
4. Persist and audit every proposed call.
5. Validate it with `ISecurityPolicy`.
6. Reject denied calls; request consent for approval-required calls.
7. Dispatch only allowed or explicitly approved calls.
8. Persist the result as a typed observation, then ask the model for the next safe step.
9. Stop when the model returns no actions; suppress already-successful or otherwise blocked duplicates and fail honestly if a bound is exhausted. If a dedicated build/test already succeeded, a planning-limit stop may complete with an explicit boundary notice while retaining every later denial in the result and audit trail. Check cancellation between every stage.

The runner returns one consistent response object containing the final natural model response and typed tool results; the same bounded rendered response is stored and shown live. Failed executions may be proposed again after the model has inspected the error, which allows compiler repair; successful, rejected, and policy-denied calls remain duplicate-protected for the task.

### Game genre and system-pack analysis

Game-generation requests receive a deterministic advisory classification before the local-model prompt is assembled. `GameGenreRegistry` maps bounded prompt vocabulary to a primary genre, up to two hybrid genre signals, a dimension/perspective, composable system-pack dependencies, and concrete validation gates. The initial catalogue covers third-person and first-person action, platformer, top-down RPG, survival crafting, racing, strategy, simulation/management, puzzle, narrative adventure, sports, rhythm, and a safe sandbox fallback. Explicit requirements such as multiplayer, procedural generation, dialogue, inventory, crafting, stealth, controller, touch, and XR add reviewed system packs without changing the selected genre.

The classification is planning context only: it creates no `ToolCall`, grants no permission, installs no package, and does not widen Unity's allow lists. Only `third_person_action` is currently certified through the Frontier Valley reference implementation; every other genre remains a prototype classification until its deterministic template, tests, and acceptance evidence are added. This separation lets ForgeCore reason broadly while execution continues to fail closed.

For game-generation tasks, the same deterministic selection is captured as a versioned `GameBlueprint` and stored against the task through the optional `IGameBlueprintStore` capability. Schema 2 adds a bounded deterministic campaign of one to twelve levels: contiguous ids, unique seeds, onboarding/escalation/finale roles, mechanic-focus packs, validation gates, and adjacent objective-completion transitions. Schema 3 adds a coherent game-art-set plan: one bounded style family plus genre-dependent environment, prop, gameplay-object, character, animation, weapon/tool, vehicle, effects, and UI slots with minimum counts and explicit PBR, rig, animation, LOD, collision, provenance, rights, visual-review, and performance gates. A deterministic readiness evaluator rejects incomplete one-off assets, mixed styles, missing rights/visual review, or absent technical coverage; it does not download, import, licence, or approve anything. Exact stored schema-2 blueprints upgrade in memory to the current derived art plan without recovering or storing the original prompt. An explicit level count is extracted and clamped without storing the prompt; otherwise three levels are planned. The blueprint contains only bounded derived data and never duplicates the user's prompt. Non-game conversations do not create blueprints. This gives future Unity executors a stable, auditable input contract without coupling the agent to a particular database implementation.

### Reviewed Unity prototype templates

Kit 0.16.29 supersedes 0.16.28 through an enumerated exact-hash upgrade and protected backup. It retains the public scene contract and real-runtime Play Mode proofs while changing the inert-by-default standalone instrumentation from a static opening-state sample to one fixed `scripted_gameplay_v1` movement/action exercise. The real project was upgraded and accepted on 26 October 2026 through compilation, EditMode/PlayMode, exact three-scene V13 build, smoke, and visible gameplay profiling.

`ScaffoldUnityGameTemplate` installs one fixed, manifest-backed source kit supporting exactly `first_person_action`, `platformer`, `top_down_rpg`, and `racing`. The write action is approval-gated, accepts no arbitrary source or package argument, is idempotent only when every listed source hash matches, and refuses modified installations without overwrite. Enumerated exact hash-verified predecessor kits may upgrade to 0.16.29 through a protected `.forgecore/unity/template-kit-backups` snapshot. The kit gives every serializable `MonoBehaviour` its own same-named script asset and validates that invariant before saving a scene, preventing unresolved local script IDs from producing a corrupted standalone `level0`. It executes a genre-specific gameplay contract during scene creation: player mode/controller, camera wiring, objective kind/count/order, trigger physics, sequential racing checkpoints, and reachable/non-premature completion. Runtime visual styling applies a render-pipeline-aware material palette, objective accents, lighting, fog, bounded level tint, and genre-specific camera projection/framing without adding packages or rewriting existing scenes. Racing checkpoints are open visual gates around a non-solid ordered trigger, keeping the route visible while retaining the gameplay contract. The kit includes a first-level start screen, pause/resume, restart/quit controls, a bounded selector for already-unlocked campaign levels, and a stable template-plus-campaign save slot that persists only the highest unlocked level through Unity `PlayerPrefs`; it does not yet persist mid-level state. FPS and top-down targets gain bounded chase/return movement, runner/walker/brute combat profiles, level-scaled multi-hit health, hit scaling, cooldown-limited contact damage, locally synthesized hit/damage/objective/fire tones, and short runtime particle bursts. First-person scenes also gain a multi-part non-colliding camera weapon, bounded magazine/reserve ammunition, timed reload, fire cadence, recoil, movement bob, and an ammo HUD. Kit 0.16.19 expands fresh first-person scenes with articulated target silhouettes, cover, towers, and colored point lights; kit 0.16.20 adds a cached deterministic 64x64 procedural surface library for ground, structure, objective, weapon, and actor materials with Built-in/URP shader-property support. Kit 0.16.24 adds a bounded typed control frame shared by normal player and actor `Update` paths plus scripted input. Its Play Mode fixture drives all four genres through start, movement, primary action, pause/no-motion, resume, respawn, and a grounded platformer jump over real elapsed frames. Kit 0.16.28 added the one-second-warmup rendered profiler. Kit 0.16.29 binds it to `scripted_gameplay_v1`, feeds bounded genre-specific frames through the normal actor controller, and records/requires gameplay frames, accumulated travel, action events, objective state, and minimum health alongside frame/GPU/memory/scene evidence; without all three private profile arguments it performs no profiling, scripted input, or file access. These remain procedural prototype visuals and simple transform steering, not licensed production art, skeletal character animation, navmesh pathfinding, or production audio/VFX. Bridge 0.17.15 exposes `create_game_template`, `create_game_campaign`, deterministic runtime `verify_gameplay`, local `profile_scene`, read-only `inspect_game_art_asset`, and non-overwriting `capture_game_art_preview`. Campaign creation accepts one supported template, a bounded seed/count, and an exact `-Level01.unity` destination; it creates one to twelve non-overwriting scenes with derived seeds, serialized level position and next-scene transitions, rolls back partial creation, and preserves the project's prior startup ordering. A campaign build must display the same first scene and count and includes exactly those linked scenes. The bridge resolves exact compiled builder contracts and never evaluates supplied C#.

Unity actions that need declared project packages may opt into locked-package mode. ForgeCore requires every direct dependency to match `packages-lock.json`, requires non-module packages to exist in the local project cache, captures both package files before launch, and restores plus blocks the result if Unity changes either file. This protection now applies consistently to compilation, scene creation, tests, Play Mode, preview capture, and builds.

Project scaffolding is deterministic application code rather than generated shell commands. Web assets can only enter a project's `.forgecore/staging` quarantine through exact allow-listed HTTPS hosts, passive extensions, a byte limit, optional publisher checksum verification, and a recorded licence manifest. Catalogue search, download staging, read-only inspection, approved import, Unity, and Blender remain separate trust boundaries.

## Reviewed local asset vault

`SearchAssetVault` is an offline read-only metadata scan of immutable bundles under the workspace-owned `.forgecore/asset-vault/objects`. A bundle is content-addressed by a canonical identity covering the exact GLB, imported provenance, source Unity metadata, four-view preview and provenance, schema-2 Unity evidence, separate approved visual and rights records, role/style/tags, measured resource counts, and Editor/bridge identity. Search never trusts a directory name alone, skips malformed entries, and performs no download or project write.

`StoreReviewedAsset` is a write approval but does not change the source project. The executor re-runs the strict Unity evidence catalog, requires current structural/performance/convention evidence and both current exact-hash human approvals, re-hashes every source file, copies into a private staging directory, verifies each copy, writes a canonical entry, and atomically moves the new bundle without overwrite. Missing, rejected, stale, malformed, changed, or merely model-claimed review state fails closed.

`ImportVaultAsset` is a separate project-scoped write approval bound to the exact bundle and GLB hashes plus a new directory under `Assets/ForgeCore/Generated/Vault`. It verifies every immutable bundle file, creates adjusted target provenance and a vault-import record in private staging, then atomically moves the whole new directory. Source `.meta` and source-project technical approval are not copied as target authority: Unity creates target metadata, and the supervised workflow compiles, inspects, previews, and obtains target-project review before placement. Named supervised 3D generation searches this vault first and reaches cloud generation only when no exact named compatible candidate is returned.

Text patches replace one exact unique selection, optionally require a matching current SHA-256, and create a protected `.forgecore/backups` snapshot before an atomic replacement. Snapshot restoration requires the current hash and creates a pre-restore safety copy. The same guarded restore can consume a `.bak` from a same-project `.forgecore/unity/backups` directory, but it cannot apply a Unity backup across projects. Dedicated .NET actions accept only a workspace project/solution path and `Debug` or `Release`; they supply an empty local package feed, invoke no shell, cap captured output, enforce a timeout, and kill the process tree when cancelled. This constrains ForgeCore's arguments but does not make untrusted MSBuild targets safe.

Interfaces deliberately leave room for future Windows automation, browser control, richer Unity providers, and Blender tools without granting those capabilities in the current release.

## Project retrieval

`IndexProject` walks an existing approved directory without following reparse points. It skips `.git`, `.forgecore`, IDE/build caches, unsupported/binary/oversized files, and filenames likely to contain credentials. Configurable file-count, per-file, and aggregate-byte limits prevent unbounded scans. Only paths and derived metadata are committed transactionally after a complete scan, so cancellation preserves the prior index.

`SearchProject` performs bounded lexical ranking across paths, extracted symbol names, and identifier terms. It returns paths, symbols, hashes, and snapshot age but no stored source snippet. The agent prompt directs the model to read current files before editing because an index is deliberately a discovery snapshot rather than edit authority.

## Online asset discovery

`SearchAssetCatalog` is the first supervised online-research primitive. Its v0.7 adapter targets the fixed anonymous Openverse API for image and audio metadata. The security policy derives `Network` permission, requires one-action approval, and can disable the feature entirely. `ToolExecutor` uses the hardened public-network HTTP transport, applies a response byte limit, filters mature/non-HTTPS/incompatible-licence records, and returns bounded source, creator, licence, attribution, preview, and direct-media metadata marked as untrusted.

The catalogue cache is process-memory only, capped at 32 queries, and expires after the configured lifetime. Raw result sets are passed to the active model planning loop but redacted by `SqliteForgeStore` and omitted by `AgentRunner` when constructing the durable conversation transcript. Search and download remain separate actions; catalogue results have no authority to bypass the asset-host allow-list or staging approval.

## Quarantine inspection and import

`InspectStagedAsset` resolves exactly one passive file and its strict manifest under `<project>/.forgecore/staging`. It recomputes SHA-256 and verifies the recorded file name, byte count, licence, source/download HTTPS URLs, and format structure. Image dimensions, WAV chunks, compressed-media signatures, OBJ geometry counts, and GLB scene/resource limits are bounded. OBJ external material libraries and every GLB URI reference are rejected.

`ImportStagedAsset` is a distinct `Write` action. Its typed call must name the same file, an in-project destination ending in that exact filename, and the inspection SHA-256. The approval dialog displays the quarantine source, destination, hash, no-overwrite rule, and provenance sidecar. Execution re-inspects, streams to a temporary file while hashing again, atomically moves the asset and sidecar into place, and rolls back a partial pair. The quarantined source is deliberately retained for audit/recovery.

## Optional 3D generation provider

`Generate3DAsset` is a typed `Network` action with exact project, provider, asset-name, prompt, and model fields. `I3DGenerationProvider` has fixed adapters for Seele API v2 and Meshy Text-to-3D v2. Meshy uses a fixed Meshy 6 preview followed by a PBR refine and accepts only the refined GLB. The policy requires an existing Unity project, the selected provider's explicit feature flag, a syntactically valid key in its configured environment variable, and one-action user approval. The bounded task-session grant deliberately excludes this tool.

Each provider sends only a guarded original-asset prompt and fixed generation parameters. It authenticates with a Bearer header, polls exact task identities with cancellation and a hard deadline, and accepts only bounded HTTPS artifact metadata. The executor downloads only passive GLB or preview-image formats using the same hardened public-network transport, streams hashes and size limits, strips query/fragment credentials from persisted URLs, stages transactionally, and immediately runs the existing structural inspector. Generated output is labelled for provider-specific rights and visual review. Generation, quarantine inspection, project import, Unity structural inspection, local preview capture, human visual acceptance, human rights acceptance, and scene placement remain separate trust decisions. The supervised 3D workflow now compiles/imports the exact GLB, requires current structural-ready evidence and a valid four-view preview, then pauses separately for exact-hash visual and rights decisions before it may propose generated-asset placement; any failed, rejected, cancelled, stale, or missing gate stops the flow without modifying a scene.

## Unity bridge

`InstallUnityBridge` writes one deterministic C# Editor source file and version/hash manifest under `Assets/ForgeCore/Editor`. It is included automatically in new Unity scaffolds and refuses any existing mismatched file. `ScaffoldUnityMapDemo` separately installs the fixed/hash-verified Frontier Valley runtime and Editor builder. `UnityEditorAction` accepts only its enumerated typed operations, including the reviewed map/game-template, scene-preview, art-inspection, art-preview, and generated-asset preparation flows. Each operation has an exact argument schema; there is no arbitrary method, C# expression, command line, package, registry, or external-path field.

ForgeCore requires the configured Editor version to exactly match the project's declared version before launch. It then writes a one-use request beneath `<project>/.forgecore/unity`, passes its SHA-256 and fixed request/result paths to the configured `Unity.exe`, and launches through `ProcessStartInfo.ArgumentList` with `UseShellExecute=false`, `-batchmode`, a hard timeout, bounded logs, and process-tree cancellation. Package-disabled launches add `-noUpm`. The optional locked-package mode first requires every direct manifest dependency to be pinned in `packages-lock.json` and already present in `Library/PackageCache`; it byte-snapshots the manifest and lock file, then restores them and fails the action if Unity changes either. The bridge independently validates its protocol, request hash, project boundary, operation, scene path, and no-overwrite targets. Result protocol/bridge/editor/request/operation identity is checked before success is accepted. Request/result files are removed; local logs remain for diagnosis.

A process-local project lease serializes every ForgeCore Unity mutation, test, build, bridge/template install, generated-asset preparation, MCP call, player smoke action, and standalone profile action for the same normalized project. Different projects may proceed independently, but two ForgeCore branches cannot race Unity against one project in the same process.

`capture_scene_preview` accepts one existing `Assets/.../*.unity` scene, one traversal-free non-existing `Previews/.../*.png` destination, and a one-to-thirty-second runtime delay. Bridge 0.17.11 renders the active runtime camera synchronously to 1280x720 without `-nographics`, rejects likely unsupported-shader magenta output and blank/near-uniform frames from sampled pixels, verifies the PNG again after Unity exits, and writes an atomic schema-1 provenance sidecar bound to the scene hash, PNG hash, Editor/bridge versions, dimensions, and duration. Captures remain local and are separate approval-gated evidence; they do not certify art quality by themselves.

`verify_gameplay` accepts only an existing scene and a bounded two-to-thirty-second duration, requires the exact current template kit, and uses the same resumable Play Mode lifecycle as preview capture. After runtime initialization, bridge 0.17.11 resolves one exact `ForgeCoreGameTemplates.PrototypeGame` contract and invokes its development/editor-only deterministic check. That check exits the start/pause state, proves serialized player movement, spawn restoration, objective interaction/completion, and racing order rejection, then exits Play Mode without saving scene mutation and returns concrete distances/counts. The executor accepts only the reviewed summary grammar and atomically writes schema-1 evidence under `.forgecore/unity/gameplay-evidence`, binding the result to scene and template-manifest SHA-256 values plus Editor/bridge/kit versions. The desktop catalog groups valid history by scene and evaluates only the newest record for current/stale status, while retaining older JSON records for audit. This scene-specific evidence is complemented by the kit's multi-frame control-path Play Mode fixture; neither substitutes for feel, balance, performance telemetry, or human playtesting.

`profile_scene` accepts only an existing reviewed-template scene and a five-to-thirty-second duration. It uses the serialized Play Mode lifecycle without saving and records real elapsed intervals between Editor updates, peak allocated memory, and Unity's draw-call/SetPass/triangle/vertex counters when that context exposes them. The executor validates bounded structured metrics and atomically writes schema-2 evidence under `.forgecore/unity/performance-evidence`, bound to the scene and current template-manifest hashes plus Editor/bridge/kit identity. The record separates `editorBaselineBudgetPassed`, `renderMetricsAvailable`, and `renderBudgetPassed`; absent batch render counters can never masquerade as a render pass. This is a repeatable local Editor responsiveness/memory gate, not rendered-frame timing, player-build profiling, or target-hardware certification.

`UnityPlayerProfileTest` is a separate typed execute approval for a five-to-thirty-second development-player measurement at fixed 1280x720 windowed resolution. It requires schema-3 build provenance with exact executable, `level0`, ordered scene-source, template-kit version, and template-manifest hashes. ForgeCore writes a one-use request, passes its SHA-256 directly to the exact player without a shell, and accepts only a matching bounded result before deleting the transient request/result. The player performs a one-second warmup, samples actual standalone frame deltas, Unity GPU timings when available, allocated memory, active renderers/meshes/vertices/triangles/cameras, graphics device, and quality state, then exits itself. ForgeCore retains the bounded player log and atomically creates immutable local evidence under `.forgecore/unity/player-profile/evidence`; budget failure still preserves evidence and returns failure. The evidence explicitly qualifies the result as one workstation/resolution/content baseline, not universal hardware or final-art certification.

Unity NUnit failures are reported as a bounded diagnostic summary: at most five failed test cases with whitespace-normalized, truncated name, message, and stack text. This keeps the actual assertion visible without exposing an unbounded Editor log to the planning loop.

`inspect_game_art_asset` accepts only an imported `Assets/ForgeCore/Generated/*.glb`, its exact SHA-256, one bounded asset-set id, one typed art role, and one bounded style family. Bridge 0.17.11 imports synchronously, instantiates the asset only inside a temporary preview scene, and records mesh, renderer, material/PBR, texture, missing-resource, rig/avatar, animation, LOD, collider, triangle/vertex, bounds, texture pixels/dimensions/estimated memory, grounded-pivot offsets, root scale, and root rotation without saving a scene. The executor protects the GLB, provenance sidecar, and pre-existing `.meta`; changed metadata is atomically restored and the result rejected, while any GLB/provenance mutation is rejected. Schema-2 evidence under `.forgecore/unity/art-evidence` binds all three hashes and explicitly sets rights and visual review false. The strict catalog re-hashes current files, groups the newest record per asset set, maps only valid current structural facts into the schema-3 art plan, recognizes retained schema-1 history without treating it as current, and cannot turn this structural operation into legal or visual acceptance. For 3D styles, readiness requires measured geometry/material/texture resources and pivot/scale/orientation conventions, enforces typed per-role per-asset ingestion caps, and enforces style-family whole-pack caps. These deterministic content-ingestion budgets catch missing or obviously excessive evidence; they do not replace later scene-specific draw-call, memory, frame-time, or target-hardware testing.

`capture_game_art_preview` accepts the same exact imported GLB/hash/set identity plus one traversal-free non-existing `Previews/.../*.png` destination. Bridge 0.17.11 activates a temporary clone in Unity's verified empty unsaved batch scene, frames four deterministic angles, renders a 1280x720 atlas, rejects high-ratio error-magenta and blank/near-uniform output, and explicitly destroys all temporary objects without saving. The executor re-verifies the immutable GLB, provenance, and `.meta`, validates the PNG header and dimensions, and writes an atomic `.forgecore-art-preview.json` sidecar binding every source hash, the PNG hash, Editor/bridge versions, dimensions, and four-view count. Preview evidence is local and non-overwriting and always records `rightsReviewed=false` and `visualReviewed=false`; a successful render proves reviewability, not legal or artistic acceptance.

`review_game_art_asset` is a human-attestation action rather than a model decision. The proposal contains one review kind (`visual` or `rights`), asset-set identity, exact GLB and preview paths, and exact GLB, preview, and preview-sidecar SHA-256 values, but it cannot contain a decision. The ordinary native-model tool parser cannot emit this action, trusted-project sessions cannot authorize it, compact approval-inbox controls cannot approve it, and closing the full dialog records nothing. Only a live user approval or rejection is bound internally by `AgentRunner`; execution then re-hashes the GLB, imported provenance, `.meta`, PNG, and preview sidecar, strictly checks their identity plus current Editor/bridge provenance, and atomically writes a non-overwriting record under `.forgecore/unity/art-reviews`. Visual and rights records are separate. The newest valid exact-hash record controls each flag; rejection keeps the flag false, later exact-hash approval can supersede it, and any source/preview change makes the old record stale. This prevents the model, a stale preview, or a forged tool argument from self-certifying art or licence acceptance.

Existing scene mutations create a protected pre-change snapshot. Scene creation registers the new scene as enabled in Build Settings and snapshots an existing `EditorBuildSettings.asset` before that change. New scenes, installed bridges, Windows `.exe`/`_Data` build pairs, and bridge results never overwrite. Test execution uses Unity Test Framework's fixed command-line surface and parses bounded, DTD-disabled NUnit XML. Project C# and Unity build callbacks remain executable code running as the current normal user; the bridge narrows ForgeCore's request surface but is not an OS sandbox.

Every successful Windows build now produces an atomic schema-3 provenance sidecar bound to the Editor version, development flag, ordered scene count/path/source hashes, executable SHA-256, serialized `level0` SHA-256, and the template-kit version/manifest hash when present. `UnityPlayerSmokeTest` is a separate typed execute approval that accepts only the exact `Builds/.../*.exe`, re-verifies the player hashes and provenance structure, launches that player headlessly for 5-30 seconds without a shell, scans its bounded local log for crash/corruption/exception markers, and terminates only the process tree it created. Schema-1 and schema-2 build evidence remain readable for smoke-test compatibility; standalone profiling deliberately requires current schema 3 plus a development build. A build is therefore distinguishable from verified startup and measured rendered performance rather than any of those claims being treated as equivalent.

`prepare_generated_asset` binds an imported GLB to its exact provenance SHA-256, generated-asset directory, existing scene, unique anchor and object names, target height, collider mode, and placeholder policy. The executor rechecks the imported provenance, byte length, and streaming hash before launch. The bridge rechecks the hash, requires an existing Unity GLB importer, backs up the scene, instantiates beneath the named anchor, applies bounded uniform scale, adds static mesh or box collision, optionally hides prior placeholder visuals, saves, and returns mesh/material/performance counts. It never installs the required GLB importer or declares visual quality or rights acceptable.

Trusted-project mode is an in-memory, time/action/project-bounded pre-authorization layer consulted only after ordinary policy validation. It now covers generated-asset preparation, but cloud generation/spending, packages, publishing, credentials, destructive actions, commands, administrator access, human visual attestations, legal/rights decisions, unknown licences, and out-of-workspace access remain excluded.

The in-memory `TaskAuthorizationSession` sits after normal security-policy validation and before the approval window. It can consume only a bounded grant for one normalized project and a small fixed set of Unity, .NET, and CC0 passive-asset actions. A mismatch falls back to ordinary explicit approval. The grant is never written to configuration or SQLite and is revoked by Emergency Stop or application exit.

Manual approval requests also receive a bounded durable inbox record containing the task id, exact typed call, policy reason, status, and a maximum 24-hour expiry. A pending non-art record left by an earlier application process can be atomically claimed from `Pending` to `Executing`, loaded with its owning `AwaitingApproval` task, revalidated against the current security policy, and executed exactly once through the ordinary executor. Completion records `Executed`, `Failed`, or `Cancelled`; current-policy denial performs no tool execution. Human art attestations remain reject-only outside their full live exact-hash dialog, and closing a live dialog is cancellation with no art decision. An action interrupted after it reached `Executing` is deliberately not replayed automatically because its external side effects may be ambiguous. Explicit unattended requests may persist one already-proposed offline plan as an acyclic graph of at most 32 exact calls. Atomic claims release only dependency-ready steps, ordinary approvals pause only their queue, restart recovery revalidates current policy, cancellation quarantines an in-flight step, and a foreign execution owner forces manual review instead of replay. The desktop resumes at most four queues with bounded work per startup while Unity remains serialized per project. This is durable execution of an exact bounded plan, not open-ended self-directed planning or automatic invention of days of new work.

## Optional Unity MCP adapter

`UnityMcpAction` has only `discover` and `call` forms. The policy requires `Execute`, an enabled feature flag, an exact local `relay_win.exe`, a Unity project inside the workspace, the configured Editor version, a declared official `com.unity.ai.assistant` package, and a separate user approval. Calls additionally require an exact case-sensitive name in `AllowedUnityMcpTools` and one bounded JSON object.

The tool client launches only the configured relay with the fixed `--mcp` argument, no shell, redirected UTF-8 stdio, current MCP `2025-11-25` lifecycle negotiation with a small explicit backwards-compatible revision set, bounded newline-delimited JSON-RPC, a hard timeout, cancellation, and process-tree termination. It advertises no roots, sampling, elicitation, or other client capability. ForgeCore stores no Unity credentials and performs no package installation. The user binds the relay to the intended Editor through Unity's first-connection approval. This path complements rather than replaces the deterministic bridge.

## Storage boundary

This workstation uses `D:\ForgeCore` for model weights, SQLite state, generated projects, and staged assets. A mandatory hosted backend is intentionally excluded: it would add credentials, availability, cost, and privacy risks without removing the need for local Unity/Blender project files. A future optional encrypted sync/backup provider may implement a separate interface, but it must never become required for local operation or silently receive conversations, source, credentials, or audit data.
